Recommendation

The answer

Move cairn's interview rules out of prompt text and into one hosted interview engine, exposed as a remote MCP connector. Start each week from a calendar invite the user already sees. Before building the engine, run a zero-build pilot with three non-CLI testers. If those testers will not explain things in their own words, the choice of surface does not matter.

Today the product rules hold for one reason: one model reads three SKILL.md files in Claude Code. A host Renier does not control will drift. ChatGPT Study Mode gives in when pushed, and Khanmigo users walked out when answers were withheld. Code can enforce one rule outright: every sentence in the note must appear in the user's transcript. A remote MCP server added once on claude.ai web also appears in the Claude mobile apps; the verifier confirmed this in Anthropic's support docs. Through the ChatGPT Apps SDK, which uses the same MCP model, the same server could reach ChatGPT. That single build covers claude.ai, phone and ChatGPT.

What you would have to believe

  • Non-terminal users want to explain things in their own words when the prompt arrives in a tool they already use. The pilot tests this before anything is built.
  • A host model will follow a server-held sequence of question, answer and next question, and the server's refusal to commit summary prose is enough to keep the craft intact. The pilot shows how much hosts drift with prompts alone. That measurement decides whether step 3 is needed.
  • Running a private hosted server for named testers does not count as publishing the repo under the pending IP release. The source never leaves the private repo; only an endpoint is exposed.
  • A GitHub account, or a hosted git fallback, is an acceptable price for a vault the user owns. A Google Drive folder backend is the fallback if testers balk.

The engine beat the Obsidian plugin. The plugin reaches only Obsidian users, needs each user's own API key, and would put Claude's text in a pane next to the note. The engine also beat a portable skills pack, which cannot enforce the rules on other hosts and has to wait for the IP release. Voice and Telegram lost on the craft constraint. Voice transcripts cannot stay grammar-fix-only without silent rewrites, and a daily question breaks the one-precise-follow-up rhythm.

Codebase Context

Cairn is a private Claude Code plugin (v0.1.0) with three skills, installed from a local-path marketplace. Every skill hardcodes one owner and his paths. The interview description reads "Capture what Renier understands…", and the vault lives at ~/dev/personal/brain.

  • /cairn:study teaches one topic hands-on. Each step hands the user a lab command or read-only query (! <command>) and a check question. It writes a study pack that Claude authors and that never counts as a note. The labs assume an engineer.
  • /cairn:interview takes ten minutes on one topic, using a fixed question set per type (concept, system, project, synthesis, person). Claude only asks questions, with one follow-up per question for precision. A "don't know" answer becomes a queue item. Review, where teaching is allowed, comes after the questions. The note is grammar-fixed only, and its invariant is: "Done when every sentence in the note, apart from headings, links and [claude] lines, appears in the transcript." The skill commits and pushes with git, and the portable vault's pre-commit hook rejects employer terms.
  • /cairn:sweep is triggered by a Friday "Brain sweep" calendar slot, which still means opening a terminal. It gathers the sources listed in cairn.toml: local Claude Code JSONL via sessions.sh, Gmail, Drive via the local gws CLI, Slack, and Granola. It extracts topic names only, routes each one to the portable or company vault, drops covered topics, and ranks the rest by dependents first. A discussion step then has the user choose, for each pick, a queue item, a study session or an interview.

Two parts tie cairn to one machine and one person: gathering, which needs local transcripts and a local CLI, and setup, which needs two vaults, a git hook, cairn.toml and a git identity per vault. Web research found the following:

  • Agent Skills became an open standard in December 2025.
  • Remote MCP connectors are account-level and reach mobile.
  • MCP Apps and the ChatGPT Apps SDK share one UI model.
  • Claude Code Routines and Cowork run scheduled jobs in the cloud, but only against a remote vault.
  • Obsidian Git describes itself as unstable on mobile.
  • OhLife's email-reply journaling died of growth and monetisation, not of the mechanic.
  • The weekly rituals that last (the GTD review, therapy homework, Toastmasters) are triggered by a calendar or another person, never by memory.

Two platform claims could not be confirmed: that uploaded claude.ai skills run on mobile, and that MCP prompts appear as slash commands in claude.ai.

Topic Axes

  1. Weekly trigger: how the ritual starts without the user remembering.
  2. The articulation act: where, and in what modality, the user explains the topic in their own words.
  3. Source gathering: what "the week's work" means for a non-engineer, and where gathering can run.
  4. Vault and setup: storage, git-free sync, first-run onboarding, one vault or two.
  5. Runtime host: where the model and the rules execute.

Ranked Ideas

  • 1. Hosted interview engine that enforces the craft
  • 2. Calendar invite as trigger and pick list
  • 3. Zero-build claude.ai pilot
  • 4. Setup is the first interview, vault without git
  • 5. The week interview plus a logbook replaces scraping

1. Hosted interview engine that enforces the craft

Runtime hostConfidence 65%Complexity High
Description
The engine is a private remote MCP server; one candidate host is a Cloudflare Worker with a Durable Object per session. It owns the question tables, a server-side ten-minute clock and the verbatim transcript. Tools: start_interview, record_answer, commit_note, list_picks. commit_note rejects any non-heading sentence that is neither in the stored transcript nor marked [claude], then writes the markdown to the user's vault. An MCP App card renders the weekly picks and the read-back. Email and other channels later become thin adapters over the same engine.
Who it reaches
Anyone on paid claude.ai, on the web and in the iOS and Android apps. ChatGPT users can follow through the Apps SDK.
Weekly user action
Open the chat app they already use, tap a pick on the card, answer the questions, and confirm the read-back.
Build cost
Large: hosting, OAuth, a vault write path and an MCP App UI.
Must believe
Hosts follow the server's tool sequence. A normalised sentence match tolerates grammar fixes. Users will add one custom connector.
Basis
direct: skills/interview/SKILL.md step 6, "Done when every sentence in the note, apart from headings, links and [claude] lines, appears in the transcript". The invariant can already be checked by a machine. external: the verifier confirmed in Claude support docs that remote connectors added on the web work on mobile. MCP Apps and the ChatGPT Apps SDK share the iframe-over-MCP model. ChatGPT Study Mode gives in under pressure, which shows that prompt-only rules fail.
Rationale
This is the only candidate that keeps the product rules intact on hosts Renier does not control. Every other surface becomes a shell over this engine instead of a rewrite.
Downsides
It is the biggest build. The check guards the committed note, not Claude's turns, so a host can still teach mid-interview, and the server can only limit that by owning the question text. Bad input, such as autocorrect or quoted email, passes the check, so the read-back stays mandatory.

2. Calendar invite as trigger and pick list

Weekly triggerConfidence 75%Complexity Low
Description
A scheduled sweep runs as a Claude Code Routine against a remote vault and writes sweep/YYYY-MM-DD-proposal.md with checkboxes. It then creates tentative ten-minute "Explain: <topic>" events in the user's calendar, placed near their usual session time. Each event's description carries the reason for the topic (for example, "three topics build on it") and a link to the user's surface. Accepting an event picks the topic and declining it queues the topic, and both write back to the proposal file, so markdown stays the record.
Who it reaches
Anyone with Google Calendar, the owner included, starting this month.
Weekly user action
RSVP to about three invites, then attend the ones accepted.
Build cost
Small to medium: a Routine, a Calendar API write, and syncing RSVPs back to the proposal file.
Must believe
An RSVP can replace the sweep discussion. The "confirm proposed depends links" step then moves to the opening of each interview.
Basis
direct: skills/sweep/SKILL.md line 3, "…or at the Friday "Brain sweep" calendar slot", and "Thirty minutes, once a week." The calendar already triggers the sweep but leads to a terminal. external: Routines run scheduled jobs on Anthropic's infrastructure. The GTD weekly review, therapy homework and Toastmasters are triggered by a calendar or another person. Duolingo's reminders work best about 23.5 hours after the last session.
Rationale
It fixes the stated failure, that even the owner forgets Friday, without asking anyone to install a new app. It also splits a 30-minute block people skip into a few seconds of RSVPs and short sessions they have committed to.
Downsides
It is a trigger, not a surface: the link needs an interview surface behind it. A Routine needs the vault on a remote. Calendar fatigue is real.

3. Zero-build claude.ai pilot

Runtime hostConfidence 70%Complexity Low
Description
Parameterise the three skills by replacing "Renier" and the hardcoded paths with values the user states at first run. Zip them and hand them privately to three testers, who upload them under claude.ai Customize > Skills. A recurring calendar event links to claude.ai. Notes come back as .md downloads that the tester drops into an Obsidian vault on iCloud or Drive. The pilot measures two things: whether testers finish interviews, and whether the host keeps to the question-only rule without server enforcement.
Who it reaches
Three to five named claude.ai Pro or Max testers, with nothing published.
Weekly user action
Tap the calendar link, run one interview in chat, and save the note.
Build cost
Small: one session of parameterising.
Must believe
The skills run in claude.ai without filesystem access, given that git and sessions.sh drop out. Saving the note by hand does not kill the habit within four weeks.
Basis
direct: the interview skill's description hardcodes "Capture what Renier understands…". external: claude.ai accepts per-user skill uploads on Pro and Max with code execution. reasoned: this is the knock-out test for the whole tree. If people without a terminal will not do the articulation, no surface will save the product.
Rationale
It answers the riskiest assumption, that the target users will do the work, for almost no cost. It also produces the drift data that decides whether idea 1 is worth building.
Downsides
Mobile support for uploaded skills is unconfirmed, so testers should use desktop or web. Saving notes by hand understates the real experience.

4. Setup is the first interview, vault without git

Vault and setupConfidence 60%Complexity Medium
Description
First run is a question-only interview about the user's work. It asks who pays them, whether an employer owns ideas that must stay separate, where the week leaves traces, and what they want to be able to explain in a year. Their answers become their first note. A [claude] section turns the answers into cairn.toml, a choice of one vault (no employer) or two, and the employer-term list. The vault is created and written through a small adapter: read, write with a message, list changes. The adapter has backends for the GitHub API or a Drive folder, so the user never runs git, and the employer-term check runs in the adapter instead of a local hook.
Who it reaches
Every new user. It decides whether a freelancer with no employer or a business owner gets started at all.
Weekly user action
None after setup. The user re-runs it when their work changes.
Build cost
Medium: a new question set, config mapping, and two storage backends.
Must believe
Conversational answers are enough to configure sources. Users will grant repo or Drive access to a hosted writer.
Basis
direct: the routing test "would the note still be true after Renier leaves this company?", and interview step 10, "git add -A && git commit … then push the company vault. The portable vault's pre-commit hook rejects company terms". external: Obsidian Git describes itself as "highly unstable on mobile". OhLife users treated owned plain text as a trust signal.
Rationale
Setup is the largest wall for non-engineers. Making it an interview means the first five minutes show the product's promise, your words becoming a note, instead of a config screen.
Downsides
Moving the employer-term check off the git hook weakens the leak guarantee unless the adapter blocks writes just as strictly. Non-engineers may not have GitHub, which makes the Drive backend necessary.

5. The week interview plus a logbook replaces scraping

Source gatheringConfidence 65%Complexity Low
Description
For users with nothing to scrape, the sweep opens with a fixed five-question "week" set, for example: "What did you have to look up?", "Where did you bluff?", "What did a client ask that you couldn't answer crisply?". Topic names come from the user's own answers. During the week the user can also append a line to log.md by forwarding an email to a private address or using a phone share-sheet shortcut. Connector sources (Gmail, Calendar, Drive, Granola) stay optional extras tagged runtime = connector in cairn.toml. Local-only sources such as sessions.sh are skipped on hosted runs, with one line saying so.
Who it reaches
Small business owners and freelancers whose work leaves no digital trail, and every hosted run.
Weekly user action
Log a few lines during the week, then answer five short questions before picking.
Build cost
Small: one question set, a sweep mode that skips gathering, and an email-to-log worker.
Must believe
People can name their gaps from memory when prompted with questions like "where did you bluff?". Logging happens often enough without a streak.
Basis
direct: sweep step 3, "Never copy wording from meetings or Slack: those are other people's words, and only topic names leave this step." The user's own answers are the one source the rules fully allow. The evidence dossier notes that sessions.sh reads local JSONL and so cannot run from a hosted runtime. external: email and messaging journaling products capture with no install.
Rationale
It removes every OAuth flow and local dependency from the critical path, so a hosted or phone sweep works on day one. Recalling the week is itself practice at explaining.
Downsides
Recall without evidence finds fewer gaps than scraping does. Ranking by dependents still needs some depends: links to exist before it has anything to rank.

6. Interview by email thread

The articulation actConfidence 45%Complexity Medium
Description
On Friday an email lists two or three ranked gaps, and replying "2" starts that topic's question set. Each email carries one question, and each reply is stored as a verbatim turn after quoted text and signatures are stripped. Cairn sends at most one precision follow-up per answer. The session closes after a stated silence window, which replaces the ten-minute clock. The review, where teaching is allowed, arrives as a separate later email, with the note inline and attached as .md. Replying with edits counts as the read-back. It runs on the engine from idea 1, with Cloudflare Email Routing and Sending as the channel.
Who it reaches
Anyone with email, including people who will never add a connector or install an app.
Weekly user action
About six replies in one thread over a day or two.
Build cost
Medium: inbound parsing, thread state and deliverability.
Must believe
Answers written hours apart stay precise enough for one follow-up to sharpen them. Stripping quoted text is reliable enough to treat a reply as the transcript.
Basis
direct: interview step 2, "One question per turn, as plain chat text. One follow-up per question, asking for precision". Review is already a separate later step, so separate emails keep the no-teaching rule. external: OhLife and the Readwise daily email show that a reply-to-email habit works. OhLife's export complaints argue for attaching the markdown.
Rationale
It is the widest-reach surface that still makes the user write every sentence, and it needs nothing installed.
Downsides
The verifier rated it weak. The silence window loosens the clock, and replies pick up autocorrect and quoted text, so the read-back has to catch input noise. Build it only after the pilot shows demand.

Rejection Summary

The five ideation agents produced 40 raw candidates across six frames. Merging duplicates left 17 candidates plus 4 combinations. A separate verifier then rated each one. Duplicates and prerequisites were folded into the survivors: the connector manifest and logbook went into idea 5, the vault adapter and one-click vault into idea 4, and the proposal file into idea 2.
